# เอกสารสรุปโปรเจค: แอปติดตามโภชนาการจากเครื่องชั่งน้ำหนักอัจฉริยะ (DIY Smart Nutrition Scale)

> เอกสารนี้สรุปผลการรีเสิร์ชสำหรับไอเดียโปรเจค — แอปมือถือที่รับค่าน้ำหนักจากเครื่องชั่งดิจิตอลที่สร้างขึ้นเอง แล้วคำนวณแคลอรี่/สารอาหาร พร้อมระบบ TDEE และกราฟติดตามเป้าหมายรายวัน
> จัดทำ: สิงหาคม 2026 (ข้อมูลราคา/บริการอาจเปลี่ยนแปลง ควรตรวจสอบซ้ำก่อนตัดสินใจจริง)

---

## 1. ภาพรวมโปรเจค

โปรเจคนี้ประกอบด้วย 2 ส่วนหลักที่ทำงานร่วมกัน:

1. **Hardware** — เครื่องชั่งน้ำหนักดิจิตอล DIY ที่มีปุ่มกดส่งค่าน้ำหนักไปยังแอปผ่านไร้สาย (BLE หรือ WiFi)
2. **Software (Mobile App)** — รับค่าน้ำหนัก ให้ผู้ใช้เลือกว่าเป็นวัตถุดิบอะไร แล้วคำนวณแคลอรี่/สารอาหารจากฐานข้อมูลโภชนาการ พร้อมคำนวณ TDEE ของผู้ใช้ และแสดงผลเป็นกราฟเทียบกับเป้าหมายรายวัน

แนวคิดนี้ไม่ใช่เรื่องใหม่ในตลาด (มีสินค้าเชิงพาณิชย์แบบนี้อยู่แล้ว เช่น Etekcity, Cosori, Ataller, Greater Goods) แต่จุดต่างของโปรเจคนี้คือ **สร้างเครื่องชั่งเอง** ซึ่งเปิดโอกาสให้ปรับแต่งได้เต็มที่ เช่น เพิ่มฐานข้อมูลอาหารไทยเฉพาะ หรือออกแบบ UX ที่เหมาะกับผู้ใช้กลุ่มเป้าหมายของตัวเอง

## 2. สถาปัตยกรรมระบบโดยรวม

```

   เก็บ log การกิน, โปรไฟล์ผู้ใช้, เป้าหมาย TDEE
        │
        ▼
[หน้า Dashboard: กราฟแคลอรี่/สารอาหารรายวัน เทียบเป้าหมาย]
```

## 3. Hardware: เครื่องชั่งน้ำหนักดิจิตอล DIY

### 3.1 ส่วนประกอบหลัก (Bill of Materials)

| ชิ้นส่วน | ตัวเลือกแนะนำ | หมายเหตุ |
|---|---|---|
| Load Cell | Single-point load cell (แบบแท่งอะลูมิเนียม) ขนาด 1–5 kg | เลือก capacity ให้พอดีกับช่วงน้ำหนักที่จะชั่งจริง (วัตถุดิบทำอาหารมักไม่เกิน 2–3 kg) ยิ่ง capacity ต่ำ ความละเอียดยิ่งดีที่น้ำหนักน้อย |
| ADC / Amplifier | HX711 (24-bit ADC) | เป็นมาตรฐานสำหรับงาน DIY เพราะมีไลบรารีและตัวอย่างโค้ดจำนวนมาก อ่านค่าจาก Wheatstone bridge ของ load cell ที่มีสัญญาณเล็กมาก |
| Microcontroller | ESP32-C3 (มี WiFi+BLE) หรือ nRF52840 (BLE ล้วน ประหยัดไฟกว่า) | ดูรายละเอียดเปรียบเทียบในหัวข้อ 3.2 |
| จอแสดงผล | OLED ขนาด 0.96"–1.3" (I2C) | ใช้แสดงน้ำหนักสด ๆ บนตัวเครื่องระหว่างชั่ง |
| ปุ่มกด | ปุ่ม tactile switch 2–3 ปุ่ม | อย่างน้อย: Tare (ศูนย์), ส่งค่า (Send), เปลี่ยนหน่วย |
| แบตเตอรี่ | LiPo 3.7V 500–1000mAh + IC ชาร์จ USB-C (เช่น TP4056) | บอร์ดตระกูล Seeed XIAO และ Adafruit Feather มีวงจรชาร์จในตัวอยู่แล้ว |
| โครงเครื่อง | พิมพ์ 3D (PLA/PETG) หรือดัดแปลงเครื่องชั่งราคาถูกที่มีอยู่แล้ว | มีไฟล์ 3D enclosure สำเร็จรูปให้ดาวน์โหลดฟรีจากชุมชนเมกเกอร์ |

ตัวอย่างต้นทุนรวมจากโปรเจค DIY จริง (ไม่รวมค่าแรง/เวลา) อยู่ที่ประมาณ **250–300 บาทต่อเครื่อง** สำหรับชุด ESP32-C3 + HX711 + Load Cell + วัสดุพิมพ์ 3D<cite index="10-1">อ้างอิงจากโปรเจคที่เผยแพร่ ต้นทุนรวมชิ้นส่วนอยู่ที่ประมาณ 7.63 ยูโร โดยใช้ ESP32-C3 Super Mini, โมดูล HX711, และ load cell ขนาด 1–20 กก.</cite>

### 3.2 การเลือก Microcontroller: ESP32 vs ESP32-C3 vs nRF52840

จุดสำคัญที่สุดของเครื่องชั่งพกพาคือ **อายุแบตเตอรี่** เพราะเป็นอุปกรณ์ที่ต้อง "หยิบมาใช้" ไม่ใช่เสียบปลั๊กตลอดเวลา

- **ESP32 (คลาสสิก):** <cite index="62-1">ไม่ใช่ตัวเลือกที่ประหยัดพลังงานที่สุด แม้จะมี deep-sleep mode ที่ดี แต่วงจรไร้สายเพียงอย่างเดียวก็กินพลังงานมากกว่าชิปประหยัดพลังงานพิเศษหลายรุ่น</cite> เหมาะถ้าต้องการ WiFi ด้วย (เช่น อยากให้เครื่องชั่งเชื่อมต่ออินเทอร์เน็ตโดยตรง)
- **ESP32-C3:** รุ่นย่อยที่เบาและประหยัดไฟกว่า ESP32 ตัวเต็มมาก มี WiFi+BLE ในตัว เหมาะเป็นจุดเริ่มต้นที่สมดุลระหว่างความง่ายในการพัฒนา (ไลบรารี/ตัวอย่างโค้ดเยอะ) กับพลังงาน
- **nRF52840:** <cite index="60-1">ให้พลังงานที่ประหยัดกว่า ESP32 อย่างชัดเจน แต่ไม่มี WiFi ในตัว ต้องใช้ BLE หรือโปรโตคอลแบบ low-power mesh อื่น ๆ</cite> ถ้าออกแบบเครื่องชั่งให้สื่อสารกับแอปมือถือผ่าน BLE เพียงอย่างเดียว (ซึ่งเหมาะกับ use case ของเรามากที่สุด) nRF52840 จะให้อายุแบตเตอรี่ที่ยาวนานกว่ามาก

**คำแนะนำ:** เริ่มต้นด้วย ESP32-C3 (เช่นบอร์ด Seeed XIAO ESP32-C3) เพราะมีตัวอย่างโค้ดและ community เยอะกว่า พัฒนาโปรโตไทป์ได้เร็ว แล้วค่อยพิจารณาย้ายไป nRF52840 (เช่น Seeed XIAO nRF52840 หรือ Adafruit Feather nRF52840) ในเวอร์ชันโปรดักชันที่ต้องการอายุแบตเตอรี่ยาวขึ้น<cite index="66-1">เพราะบอร์ดตระกูลนี้ออกแบบมาสำหรับงาน BLE ที่เน้นโหมด sleep เป็นหลัก ให้อายุแบตเตอรี่ที่ยาวกว่า ESP32 อย่างชัดเจน</cite>

### 3.3 Load Cell + HX711

หลักการทำงาน: load cell แปลงน้ำหนัก/แรงเป็นสัญญาณไฟฟ้าที่เล็กมาก (เป็น Wheatstone bridge) ซึ่ง MCU อ่านค่าตรง ๆ ไม่ได้ ต้องผ่าน HX711 ซึ่งเป็นชิปขยายสัญญาณและแปลงเป็นดิจิตอลแบบ 24-bit ก่อน<cite index="2-1">HX711 จึงเป็นจุดเริ่มต้นที่ดีมากสำหรับโปรเจค DIY เพราะให้ความยืดหยุ่น ต้นทุนต่ำ และใช้งานได้หลากหลาย</cite> ขั้นตอนสำคัญที่ห้ามข้ามคือ **การ calibrate** — ต้องใช้วัตถุที่รู้น้ำหนักแน่นอน (เช่น ถ้วยตวงน้ำ 300 กรัม) มาเทียบเพื่อหาค่า calibration factor ของ load cell แต่ละตัว เนื่องจากแต่ละตัวมีค่าไม่เท่ากัน

**ข้อควรระวังเรื่องความแม่นยำ:** สำหรับงานชั่งวัตถุดิบอาหารที่บางครั้งต้องการความละเอียดถึงระดับกรัมเดียว (เช่น เครื่องเทศ) ควรเลือก load cell capacity ต่ำ (เช่น 1–3 kg แทนที่จะเป็น 5–20 kg) เพราะความละเอียดของสัญญาณจะดีกว่าที่น้ำหนักน้อย ๆ

### 3.4 การเชื่อมต่อไร้สาย: BLE vs WiFi

| | BLE | WiFi |
|---|---|---|
| พลังงาน | ประหยัดกว่ามาก เหมาะกับอุปกรณ์แบตเตอรี่ | กินไฟมากกว่า |
| ความหน่วง/ความซับซ้อน | ต้องจัดการ GATT service/characteristic ในแอป | ง่ายกว่า (ส่งเป็น JSON ผ่าน HTTP ได้เลย) |
| ต้องพึ่งอินเทอร์เน็ต | ไม่ต้อง (เชื่อมตรงกับมือถือ) | ต้องมี WiFi network ในบริเวณนั้น |
| เหมาะกับ | เครื่องชั่งพกพา ใช้ในครัว | เครื่องชั่งที่ตั้งอยู่กับที่ ต่อ WiFi บ้านตลอด |

สำหรับ use case ของโปรเจคนี้ (ชั่งวัตถุดิบในครัว แล้วส่งเข้าแอปมือถือทันที) **BLE เหมาะสมกว่า** เพราะไม่ต้องพึ่ง WiFi router และประหยัดแบตฯ กว่า มีตัวอย่างโปรเจคที่ทำสำเร็จแล้วโดยใช้ ESP32 + BLE Server + Characteristic ส่งค่าน้ำหนักไปยังแอป ซึ่งสามารถใช้เป็นจุดเริ่มต้นได้เลย<cite index="9-1">โดยเริ่มจากการต่อวงจร ESP32 กับ load cell และ HX711 amplifier ตามผังการต่อสาย จากนั้นเขียนโปรแกรมด้วย PlatformIO โดยตั้งค่า Service UUID ของ BLE ให้ MCU ทำหน้าที่เป็น BLE Server ที่ส่งค่าน้ำหนักผ่าน Characteristic</cite>

### 3.5 พลังงาน/แบตเตอรี่

- ใช้ LiPo battery + วงจรชาร์จ USB-C ในตัว (บอร์ดหลายรุ่นมีมาให้แล้ว)
- เปิดใช้ deep-sleep mode ของ MCU เมื่อไม่ได้ใช้งาน แล้วปลุกด้วยการกดปุ่ม (interrupt) เพื่อยืดอายุแบตเตอรี่
- ปิดจอ OLED อัตโนมัติหลังไม่มีการใช้งานช่วงหนึ่ง

### 3.6 ตัวเรือน (Enclosure)

แนะนำพิมพ์ 3D เอง เพราะควบคุมขนาด/ตำแหน่งปุ่มและช่องเสียบ USB-C ได้ตามต้องการ<cite index="4-1">มีแบบเคสสำเร็จรูปสำหรับเครื่องชั่งอัจฉริยะที่ใช้ ESP32/ESP8266 กับ HX711 เผยแพร่ให้ดาวน์โหลดฟรีบนแพลตฟอร์มแชร์งานพิมพ์ 3D</cite> สามารถนำไปดัดแปลงให้พอดีกับชิ้นส่วนที่เลือกใช้ได้

### 3.7 ต้นแบบ/แหล่งอ้างอิงที่ทำสำเร็จแล้ว

มีเมกเกอร์หลายคนทำโปรเจคลักษณะนี้สำเร็จมาแล้วและเผยแพร่วิธีทำแบบละเอียด เช่น การดัดแปลงเครื่องชั่งครัวราคาถูกให้ต่อ ESP32 เข้าไป<cite index="7-1">โดยบัดกรี load cell เข้ากับโมดูล HX711 แล้วต่อเข้ากับบอร์ด ESP32 พร้อมจอ OLED และปุ่มกด จากนั้นเขียนเฟิร์มแวร์ด้วยภาษา C++ ผ่าน Arduino IDE</cite> ซึ่งผลลัพธ์คือเครื่องชั่งที่<cite index="8-1">ส่งค่าน้ำหนักปัจจุบันออกมาเป็นรูปแบบ JSON ผ่านการเข้าเว็บเบราว์เซอร์ไปยัง IP address ของอุปกรณ์ ทำให้เชื่อมต่อกับระบบอื่นได้ง่าย เช่น Home Assistant</cite> — แนวทางนี้ใช้เป็นจุดเริ่มต้นศึกษาก่อนปรับมาใช้ BLE ได้

## 4. Firmware (โปรแกรมของเครื่องชั่ง)

แนะนำใช้ **Arduino IDE หรือ PlatformIO** เขียนด้วย C++ (เป็นมาตรฐานของวงการ ESP32)

Flow การทำงานหลักที่ควรมี:
1. Boot → tare อัตโนมัติ หรือรอผู้ใช้กดปุ่ม tare
2. อ่านค่าจาก HX711 อย่างต่อเนื่อง → แสดงบนจอ OLED
3. เมื่อค่าน้ำหนักนิ่ง (stable) ในช่วงเวลาหนึ่ง → เปิดใช้ปุ่ม "ส่งค่า"
4. เมื่อกดปุ่มส่งค่า → ส่งข้อมูลผ่าน BLE characteristic (payload เช่น `{"weight_g": 152.4}`)
5. เข้าสู่ deep-sleep หลังไม่มีการใช้งาน

ไลบรารีที่แนะนำ: `HX711_ADC` (รองรับการ smoothing และ calibration) ร่วมกับ BLE stack ของ ESP32 (`BLEServer`, `BLECharacteristic`)

## 5. Mobile App

### 5.1 เลือก Framework: React Native vs Flutter

ทั้งสองตัวใช้งานได้จริงกับ BLE แต่มีจุดเน้นต่างกัน:

- **React Native:** <cite index="41-1">เหมาะเมื่อประโยชน์หลักคือการเชื่อมต่อกับฮาร์ดแวร์/SDK เชิงลึกและต้องการความรู้สึกใกล้เคียง native</cite> มี library BLE ให้เลือก 2 ตัวหลักคือ `react-native-ble-plx` และ `react-native-ble-manager` ซึ่งทั้งคู่<cite index="38-1">รองรับการสังเกตสถานะ Bluetooth adapter, การสแกนหาอุปกรณ์, การเชื่อมต่อ, การค้นหา service/characteristic, และการทำงานในโหมด background บน iOS</cite>
- **Flutter:** <cite index="41-1">เหมาะกว่าเมื่อต้องการดีไซน์ที่สม่ำเสมอทุกอุปกรณ์แบบพิกเซลต่อพิกเซล และแอปเน้นแอนิเมชันหรือการแสดงข้อมูลสดจำนวนมาก</cite> ซึ่งตรงกับความต้องการของแอปติดตามสารอาหารที่มีกราฟเยอะ ไลบรารี BLE ที่นิยมคือ `flutter_blue_plus`

**คำแนะนำ:** ถ้าทีมถนัด JavaScript/React มาก่อน ใช้ React Native ได้เลย (community ใหญ่ ตัวอย่างเยอะ) แต่ถ้าต้องการกราฟและ UI ที่สวยงามลื่นไหลตั้งแต่ต้น Flutter จะได้เปรียบเรื่องการ render กราฟ/แอนิเมชัน

ไม่ว่าจะเลือกฝั่งไหน ควรวางแผนเรื่อง<cite index="42-1">การจัดการพฤติกรรม Bluetooth ที่แตกต่างกันในแต่ละแพลตฟอร์มตั้งแต่ต้นโปรเจค รวมถึงข้อจำกัดของระบบปฏิบัติการมือถือที่จำกัดการทำงานของ Bluetooth เมื่อแอปอยู่ใน background</cite>

### 5.2 Flow การใช้งานหลัก (User Flow)

1. เปิดแอป → สแกนหา BLE device (เครื่องชั่งของเรา) → เชื่อมต่อ
2. ผู้ใช้วางวัตถุดิบบนเครื่องชั่ง → กดปุ่ม "ส่งค่า" ที่ตัวเครื่อง
3. แอปรับค่าน้ำหนักแบบ real-time ผ่าน BLE notification
4. แอปแสดง popup/หน้าค้นหา ให้ผู้ใช้เลือกวัตถุดิบ (ค้นหาจากฐานข้อมูล หรือเลือกจากรายการโปรด/ประวัติที่เคยใช้)
5. ระบบคำนวณแคลอรี่/สารอาหารจากน้ำหนักที่ชั่งได้ทันที → บันทึกลง log มื้ออาหารวันนี้
6. อัปเดตกราฟสะสมของวัน เทียบกับเป้าหมาย TDEE/สารอาหาร

### 5.3 ฟีเจอร์ UI ที่ควรมีตั้งแต่ MVP

- หน้าค้นหาวัตถุดิบ (พร้อม autocomplete)
- หน้าตั้งค่าโปรไฟล์ผู้ใช้ (อายุ เพศ ส่วนสูง น้ำหนัก ระดับกิจกรรม) เพื่อคำนวณ TDEE
- Dashboard กราฟรายวัน/รายสัปดาห์ (แคลอรี่ + macro: โปรตีน/คาร์บ/ไขมัน)
- ประวัติการกินย้อนหลัง
- ฟังก์ชัน tare สะสม (ชั่งหลายวัตถุดิบต่อกันในชามเดียวแล้วให้แอปคำนวณผลรวมอัตโนมัติ) — เป็นฟีเจอร์ที่สินค้าคู่แข่งในตลาดมีอยู่แล้วและผู้ใช้ชื่นชอบ<cite index="49-1">โดยใช้ฟังก์ชัน tare เพิ่มวัตถุดิบทีละอย่างในชามเดียว แล้วให้ระบบรวมยอดข้อมูลโภชนาการของทั้งจานให้อัตโนมัติ</cite>

## 6. ฐานข้อมูลโภชนาการ (Nutrition Database)

นี่คือส่วนที่สำคัญที่สุดส่วนหนึ่งของแอป เพราะความแม่นยำของข้อมูลโภชนาการเป็นหัวใจของทั้งระบบ

### 6.1 ตัวเลือกฐานข้อมูลสากล

| ผู้ให้บริการ | ราคา | จุดเด่น | ข้อจำกัด |
|---|---|---|---|
| **USDA FoodData Central** | ฟรี | <cite index="11-1">เป็นผู้ให้บริการรายเดียวในกลุ่มที่เปิดให้ใช้ฟรี ครอบคลุมอาหารทั้งแบรนด์และไม่มีแบรนด์ราวสองแสนห้าหมื่นรายการ อัปเดตข้อมูลทุกเดือน</cite> | เป็นข้อมูลอาหารสไตล์อเมริกันเป็นหลัก ไม่มีอาหารไทย |
| **Nutritionix** | เริ่มต้นราคาสูง (หลักพันดอลลาร์/เดือนสำหรับ enterprise) | <cite index="12-1">เน้นข้อมูลอาหารแบรนด์และร้านอาหารกว่า 800,000 รายการจากเชนร้านอาหารหลัก</cite> | ราคาแพงมากสำหรับโปรเจคเริ่มต้น |
| **Edamam** | ฟรี→999 USD/เดือน | <cite index="14-1">แปลงสูตรอาหารเป็นข้อมูลโภชนาการโดยใช้ natural language processing และมีฐานข้อมูลกว่า 900,000 รายการ</cite> | แบ่งเป็น 3 API แยกราคากัน (nutrition/food database/recipe) |
| **Open Food Facts** | ฟรี (crowdsourced) | <cite index="15-1">ครอบคลุมบาร์โค้ดสินค้ามากกว่า 2.5 ล้านรายการ 180+ ประเทศ</cite> | คุณภาพข้อมูลไม่สม่ำเสมอ เพราะเป็นข้อมูลจากชุมชน |

### 6.2 ฐานข้อมูลอาหารไทย — จุดสำคัญที่ควรใช้เป็นแกนหลัก

เนื่องจากผู้ใช้เป้าหมายน่าจะกินอาหารไทยเป็นหลัก (เช่นตัวอย่าง "ข้าว" ที่ยกมา) ฐานข้อมูลสากลอย่าง USDA จะไม่ครอบคลุมเมนู/วัตถุดิบไทยหลายอย่าง จึงควรใช้ **Thai Food Composition Database (Thai FCD)** ของสถาบันโภชนาการ มหาวิทยาลัยมหิดล (INMU) เป็นแกนหลัก:

- <cite index="20-1">เป็นฐานข้อมูลองค์ประกอบอาหารไทยที่พัฒนาโดยสถาบันโภชนาการ มหาวิทยาลัยมหิดล ซึ่งเป็นศูนย์ข้อมูลอาหารประจำภูมิภาคของ INFOODS โดยเวอร์ชันล่าสุด (Version 3, สิงหาคม 2025) ได้รวบรวมและปรับปรุงข้อมูลจากตารางองค์ประกอบอาหารไทยฉบับปี 2015 และ 1999 ให้สอดคล้องตามมาตรฐาน FAO/INFOODS</cite>
- มีเว็บไซต์ให้ค้นหาโดยตรงที่ inmu.mahidol.ac.th/thaifcd (ควรติดต่อสถาบันเพื่อสอบถามสิทธิ์การนำข้อมูลไปใช้ในเชิงพาณิชย์/แอปของตัวเอง)
- มีชุดข้อมูลที่ถูกแปลงเป็น dataset สำหรับนักพัฒนาอยู่บ้างแล้ว เช่นบน Hugging Face<cite index="23-1">ซึ่งมีแหล่งที่มาจากตารางองค์ประกอบอาหารไทยปี 2015 ของสถาบันโภชนาการ มหาวิทยาลัยมหิดล</cite> (ควรตรวจสอบสัญญาอนุญาตการใช้งานก่อนนำไปใช้จริง)
- มีงานวิจัยที่พัฒนาระบบ AI ประเมินโภชนาการอาหารไทยจากรูปภาพแล้ว (INMU iFood) <cite index="25-1">ซึ่งรองรับการนำเข้าข้อมูลอาหารเพิ่มเติมผ่านการสแกนบาร์โค้ดโดยเชื่อมกับฐานข้อมูล Open Food Facts ด้วย</cite> — เป็นแนวทางที่น่าศึกษาสำหรับการต่อยอดในอนาคต (เช่น เพิ่มฟีเจอร์ถ่ายรูปอาหารแทนการเลือกจากรายการ)

### 6.3 กลยุทธ์ฐานข้อมูลที่แนะนำ (แบบผสม/Hybrid)

1. **ชั้นแกนหลัก:** สร้างฐานข้อมูลของตัวเองใน Backend โดย import ข้อมูลจาก Thai FCD สำหรับวัตถุดิบ/เมนูไทยที่ใช้บ่อย (ข้าว เนื้อสัตว์ ผัก เครื่องปรุงไทย ฯลฯ) — ควบคุมคุณภาพและความเร็วในการค้นหาได้เอง ไม่ต้องพึ่ง API ภายนอกตลอดเวลา
2. **ชั้นเสริม:** เชื่อมต่อ USDA FoodData Central (ฟรี) สำหรับวัตถุดิบสากล/นำเข้า ที่ไม่มีใน Thai FCD
3. **ชั้นขยาย (อนาคต):** เชื่อมต่อ Open Food Facts สำหรับการสแกนบาร์โค้ดสินค้าสำเร็จรูป

## 7. การคำนวณ TDEE และสารอาหาร

### 7.1 สูตรคำนวณ BMR (Basal Metabolic Rate)

แนะนำใช้สูตร **Mifflin-St Jeor** เพราะมีความแม่นยำสูงที่สุดในบรรดาสูตรที่ใช้กันแพร่หลาย: <cite index="30-1">การศึกษาเปรียบเทียบสูตรทำนาย RMR สี่แบบพบว่าสูตร Mifflin-St Jeor มีแนวโน้มทำนายค่า RMR ได้ใกล้เคียงค่าที่วัดจริงภายในช่วง 10% มากกว่าสูตรอื่น</cite>

```
ผู้ชาย:  BMR = (10 × น้ำหนักกก.) + (6.25 × ส่วนสูงซม.) − (5 × อายุปี) + 5
ผู้หญิง: BMR = (10 × น้ำหนักกก.) + (6.25 × ส่วนสูงซม.) − (5 × อายุปี) − 161
```

### 7.2 Activity Factor (ตัวคูณตามระดับกิจกรรม)

| ระดับกิจกรรม | ตัวคูณ |
|---|---|
| นั่งทำงาน แทบไม่ออกกำลังกาย (Sedentary) | ×1.2 |
| ออกกำลังกายเบา ๆ 1-3 วัน/สัปดาห์ (Lightly active) | ×1.375 |
| ออกกำลังกายปานกลาง 3-5 วัน/สัปดาห์ (Moderately active) | ×1.55 |
| ออกกำลังกายหนัก 6-7 วัน/สัปดาห์ (Active) | ×1.725 |
| ออกกำลังกายหนักมาก/นักกีฬา (Very active) | ×1.9 |

`TDEE = BMR × Activity Factor`

### 7.3 การคำนวณสารอาหารจากน้ำหนักวัตถุดิบ

ฐานข้อมูลโภชนาการ (ไม่ว่าจะเป็น Thai FCD, USDA หรืออื่น ๆ) จะเก็บค่าสารอาหารต่อ 100 กรัมเป็นมาตรฐาน ดังนั้นสูตรคำนวณคือ:

```
สารอาหาร X ที่ได้รับ = (น้ำหนักที่ชั่งได้ (กรัม) / 100) × ค่าสารอาหาร X ต่อ 100 กรัม
```

ตัวอย่าง: ข้าวสวย 100 กรัม ให้พลังงานประมาณ 130 kcal (ตัวเลขอ้างอิงทั่วไป ควรใช้ค่าจริงจากฐานข้อมูลที่เลือกใช้) → ถ้าชั่งได้ 150 กรัม จะคำนวณเป็น 150/100 × 130 = 195 kcal

### 7.4 การแปลงสารอาหารหลักเป็นแคลอรี่ (Macro to Calorie)

ใช้ค่ามาตรฐานสากลที่ใช้กันทั่วไปในวงการโภชนาการ:

- โปรตีน 1 กรัม = 4 kcal
- คาร์โบไฮเดรต 1 กรัม = 4 kcal
- ไขมัน 1 กรัม = 9 kcal

ใช้ค่านี้ตรวจสอบความสมเหตุสมผลของข้อมูลจาก API ได้ (เช่น เอาผลรวม macro × ค่าแคลอรี่ต่อกรัม เทียบกับค่าแคลอรี่ที่ API ให้มา ถ้าต่างกันมากอาจแปลว่าข้อมูลตั้งต้นมีปัญหา)

## 8. Backend & โครงสร้างข้อมูล

### 8.1 เลือก Backend: Firebase vs Supabase

| | Firebase | Supabase |
|---|---|---|
| ประเภทฐานข้อมูล | NoSQL (Firestore) | SQL (PostgreSQL) |
| จุดเด่น | <cite index="53-1">Real-time sync ที่ทำงานได้ดีมาก เหมาะกับแอปแชทหรือแดชบอร์ดสด</cite> | <cite index="52-1">ได้ฐานข้อมูล SQL จริง มี row-level security และสร้าง REST/GraphQL API ให้อัตโนมัติ</cite> |
| เหมาะกับ | MVP ที่ต้องการ real-time เร็ว ๆ | ข้อมูลที่มีความสัมพันธ์ซับซ้อน เช่น ผู้ใช้ ↔ มื้ออาหาร ↔ วัตถุดิบ ↔ สารอาหาร |

**คำแนะนำ:** ข้อมูลของแอปนี้เป็นข้อมูลเชิงสัมพันธ์ค่อนข้างชัดเจน (ผู้ใช้ 1 คน มีหลายมื้ออาหาร แต่ละมื้อมีหลายวัตถุดิบ แต่ละวัตถุดิบมีสารอาหารหลายชนิด) ซึ่งเหมาะกับโครงสร้าง SQL มากกว่า จึงแนะนำ **Supabase** เพราะยังให้ auth, real-time (ผ่าน Postgres changefeed), และ storage แบบ all-in-one เหมือน Firebase แต่ใช้ SQL ซึ่งทำ query สรุปผล (เช่น ผลรวมแคลอรี่ต่อวัน) ได้ตรงไปตรงมากว่า

### 8.2 โครงสร้างข้อมูลเบื้องต้น (แนวคิด)

- `users` — โปรไฟล์ (อายุ เพศ ส่วนสูง น้ำหนัก ระดับกิจกรรม เป้าหมาย TDEE/macro)
- `foods` — ฐานข้อมูลวัตถุดิบ (ชื่อ, แคลอรี่/สารอาหารต่อ 100g, แหล่งที่มา เช่น Thai FCD/USDA)
- `meal_logs` — บันทึกการกิน (user_id, food_id, weight_g, timestamp, มื้อไหน)
- `daily_goals` — เป้าหมายรายวัน (คำนวณจาก TDEE หรือกำหนดเองโดยผู้ใช้)

## 11. ความท้าทายและข้อควรระวัง

1. **ความแม่นยำของ load cell ที่น้ำหนักน้อย** — เครื่องเทศ/ซอสที่ใช้ปริมาณน้อย (2-5 กรัม) ต้องการความละเอียดสูง ควรทดสอบ calibration ให้ดีในช่วงน้ำหนักต่ำ ไม่ใช่แค่ที่น้ำหนักกลาง ๆ
2. **สิทธิ์การใช้ข้อมูล Thai FCD เชิงพาณิชย์** — ควรติดต่อ INMU โดยตรงเพื่อสอบถามเงื่อนไขการนำข้อมูลไปใช้ในแอปที่จะเผยแพร่จริง (ไม่ใช่แค่งานวิจัย/การศึกษา)
3. **ข้อจำกัด background BLE บน iOS** — ระบบปฏิบัติการจำกัดการทำงานของ Bluetooth เมื่อแอปไม่ได้อยู่หน้าจอ ต้องออกแบบ flow ให้ผู้ใช้เปิดแอปค้างไว้ตอนชั่งของ
4. **การรับรองมาตรฐาน (FCC/CE) หากจะขายเชิงพาณิชย์** — ถ้าในอนาคตต้องการผลิตขายจริงและใช้ชิปไร้สายแบบ bare chip จะต้องผ่านการทดสอบ FCC/CE ซึ่งมีค่าใช้จ่ายและใช้เวลา การใช้โมดูลที่ผ่านการรับรองมาแล้ว (pre-certified module) จะช่วยลดภาระตรงนี้ได้มาก
5. **ความคลาดเคลื่อนของฐานข้อมูลอาหาร** — อาหารชนิดเดียวกันมีค่าโภชนาการต่างกันได้ตามวิธีปรุง ควรมีฟีเจอร์ให้ผู้ใช้แก้ไข/เพิ่มรายการอาหารเองได้ (custom food) ตั้งแต่ MVP

## 12. Roadmap แนะนำ

**Phase 1 — MVP (พิสูจน์แนวคิด)**
- เครื่องชั่ง: ESP32-C3 + HX711 + Load Cell + ปุ่มส่งค่า + BLE (ไม่ต้องมีจอ OLED ก็ได้ในตอนแรก)
- แอป: เชื่อมต่อ BLE รับค่าน้ำหนัก + ค้นหาวัตถุดิบจากฐานข้อมูล USDA (เร็วสุดในการเริ่มต้นเพราะฟรีและมี API พร้อมใช้)
- คำนวณ TDEE พื้นฐาน + กราฟแคลอรี่รายวันแบบง่าย

**Phase 2 — เจาะกลุ่มผู้ใช้ไทย**
- นำเข้าฐานข้อมูล Thai FCD เป็นฐานข้อมูลหลัก
- เพิ่มจอ OLED บนตัวเครื่อง + ฟีเจอร์ tare สะสม (ชั่งหลายวัตถุดิบในชามเดียว)
- เพิ่มกราฟ macro แยกโปรตีน/คาร์บ/ไขมัน

**Phase 3 — ต่อยอด**
- สแกนบาร์โค้ดสินค้าสำเร็จรูป (เชื่อม Open Food Facts)
- ฟีเจอร์ถ่ายรูปอาหารแล้วประเมินโภชนาการด้วย AI (แนวทางเดียวกับ INMU iFood)
- ย้าย MCU เป็น nRF52840 เพื่ออายุแบตเตอรี่ที่ยาวขึ้น หากต้องการผลิตขายจริง
- เชื่อมต่อกับ Apple Health / Google Fit

## 13. สรุป Tech Stack ที่แนะนำ

| ส่วน | เทคโนโลยีแนะนำ |
|---|---|
| Load Cell + ADC | Single-point load cell (1–3kg) + HX711 |
| Microcontroller | ESP32-C3 (เริ่มต้น) → nRF52840 (โปรดักชัน) |
| การสื่อสาร | BLE (GATT Service/Characteristic) |
| Firmware | C++ ผ่าน Arduino IDE / PlatformIO |
| Mobile App | Flutter (แนะนำเพราะกราฟ/UI เยอะ) หรือ React Native |
| BLE Library (มือถือ) | `flutter_blue_plus` หรือ `react-native-ble-plx` |
| Nutrition DB | Thai FCD (หลัก) + USDA FoodData Central (เสริม) |
| Backend | Supabase (PostgreSQL) |
| กราฟ | `fl_chart` / `victory-native` |
| TDEE Formula | Mifflin-St Jeor |
